# 架构说明

## 一句话

**模型负责判断，浏览器负责执行，凭证永远不出浏览器。**

插件本身不登录 QQ、不存密码，只通过 CDP 连一个"人已经登录好"的浏览器，把页面状态压缩成文本交给模型，再把模型的决策翻译成浏览器动作。

```
┌─────────────┐   工具调用    ┌──────────────────┐   CDP    ┌──────────────┐
│  DSH Agent  │ ───────────▶ │ dsh-plugin-qq-   │ ───────▶ │  Chrome      │
│  (DeepSeek) │ ◀─────────── │ pilot (本插件)    │ ◀─────── │  (已登录 QQ) │
└─────────────┘   结果/文本    └──────────────────┘  截图/DOM └──────────────┘
```

## 为什么是 CDP，不是内置浏览器

| 方案 | 登录态 | 维护成本 | 结论 |
|---|---|---|---|
| 插件内置 Playwright 下载浏览器 | 每次要重新扫码 | 高（浏览器内核几十 MB） | 否 |
| 插件自带 cookie 池 | 要处理过期、异地、指纹 | 高 | 否 |
| **CDP 连用户自己的浏览器** | 用户自己维护，天然有效 | 低 | **采用** |

好处很直接：用户在自己浏览器里扫码登录一次，插件只是"借用"这个会话；关掉浏览器，插件就没了，不存在凭证落盘的问题。

代价是：用户必须用 `--remote-debugging-port` 启动 Chrome，步数多一步，但比处理 cookie 生命周期便宜。

## 模块划分

```
src/index.ts       插件入口，只做三件事：声明 Config、注册工具、把参数转成 RuntimeConfig
src/ops.ts         所有和浏览器打交道的逻辑（连接、读页、输入、点击、二维码、限速状态）
tools/export-cookies.mjs   一次性脚本，导出 cookie JSON（可选路径）
```

刻意没有拆得更细。这个插件的复杂度在"页面不确定性"上，不在模块划分上；再多拆一层只会让改选择器时到处找文件。

### index.ts

- `export const name = 'qq-pilot'` / `export const inject = ['tools']`
- `Config` 用 Schemastery 声明，字段带默认值与描述——DSH 启动前会校验，`apply` 里拿到的 config 一定是良构的
- 每个工具都用 `defineTool({ name, description, parameters, output, execute })`
- 卸载时 `ctx.effect` 返回的处置器负责 `detach()`，只断开 CDP，不关用户的浏览器

### ops.ts

| 函数 | 职责 |
|---|---|
| `attach()` | 连 CDP，复用已有 QQ 标签页；没有就新建 |
| `emulateMobile()` | CDP 覆盖 UA / 视口 / 触摸，走手机版布局 |
| `pageDigest()` | 取会话区域 innerText 的尾部 N 字 |
| `probe()` | 扫可交互元素，生成 CSS 路径供人绑定 |
| `typeAndSend()` | 聚焦输入框 → 清空 → 逐字输入 → 点发送或回车 |
| `listCandidates()` | 读推荐列表里的昵称 |
| `clickAddFriend()` | 按昵称定位 → 找到邻近「添加」按钮 → 鼠标或触摸点击 |
| `captureQr()` | 找二维码元素（多选择器 + 最大正方形兜底）→ 裁剪截图 |
| `waitForLogin()` | 轮询 cookie 名判定登录态 |
| `loadState()` / `saveState()` | 每日计数与动作时间戳，落在系统临时目录 |

## 安全边界（写死在代码里的）

1. **Cookie 不进模型上下文。** `readCookieFile()` 只在 `addCookies()` 那一瞬间存在，不 return、不 log。
2. **加好友三重闸门**：`confirm !== true` 直接拒绝 → 超过 `dailyAddCap` 拒绝 → 小于 `minActionGapSec` 拒绝。
3. **时段闸门**：`inActiveWindow()` 不在窗口内一律拒绝动作，跨零点也支持。
4. **演练模式**：`dryRun: true` 时只走到"准备执行"，不真正敲键、不真正点击。
5. **确认弹窗不代点。** 点完「添加」就返回，把最后的「确定」留给真人。

## 为什么不用官方 QQ 机器人协议

腾讯官方的 QQ Bot 是**独立的机器人身份**，不是"你的小号"。要让小号本体说话，只有两条路：协议层登录（NapCat / Lagrange 那类，风控高）或网页端操作（本插件）。

本插件选网页端，是因为它不需要任何第三方协议实现、不存在本地存 token 的中间层；缺点是网页版功能不全、DOM 会变。

## 已知的架构性弱点

- **选择器耦合**：网页 QQ 改版即失效。缓解手段是 `qq_probe` + 配置外置，不写死在代码里。
- **单页假设**：默认只操作一个 QQ 标签页；多开小号需要多个 profile / 多个 CDP 端口。
- **文本摘要丢结构**：`pageDigest` 只给模型尾部文本，丢掉发言人归属。如果 QQ 的会话区没有明显昵称前缀，模型可能分不清谁说的。这是当前最大的语义损失点，下一步打算加"按消息节点解析"。
